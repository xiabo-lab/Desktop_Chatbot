AI Chatbot Assistant — Claude Code Project Implementation Procedure

1. Project Overview

Build a new voice-controlled AI Chatbot Assistant for a Raspberry Pi 5.

  • Raspberry Pi 5 — 8GB RAM
  • Raspberry Pi AI HAT+ 2
  • Raspberry Pi Camera Module 3
  • Texas Instruments microphone
  • Speaker
  • Touchscreen: 1280×800
  • Network connection
  • SSH: fuwenxu@aipi5.local

The system combines AIA's voice-assistant architecture, Kodama-Lite's music control, OpenAI GPT-5.6 Terra through API, camera vision, local person detection, weather, local news, and a touchscreen UI.

Reference Projects

  • AIA: https://github.com/xiabo-lab/AIA
  • Kodama-Lite: https://github.com/xiabo-lab/Kodama-Lite
Important: Do not blindly copy either project. First inspect both repositories, understand their architecture and interfaces, then reuse the appropriate components.

2. Main Objective

Create a voice-controlled AI assistant that can:

  1. Use the same wake word as AIA.
  2. Understand English, Mandarin, and Cantonese.
  3. Have normal conversations with the user.
  4. Use OpenAI GPT-5.6 Terra through API as the conversational LLM.
  5. Tell the user current weather for San Jose, CA 95127.
  6. Provide current local news.
  7. Tell child-friendly bedtime stories.
  8. Open Kodama-Lite.
  9. Use the same voice commands currently supported by AIA/Kodama-Lite.
  10. Control music through Kodama-Lite.
  11. Use Raspberry Pi Camera Module 3 to see and describe the user's surroundings.
  12. Detect whether a person is present using the camera.
  13. When nobody is present, display a weather/time screensaver.
  14. Return to the normal UI when a person comes back.
  15. Automatically start after Raspberry Pi boot.

3. Important Design Principle

Do not build everything as one large Python program. Use a modular architecture.

Microphone
    ↓
Wake Word
    ↓
STT
    ↓
Command / Intent Router
    ├── Kodama Commands → Kodama-Lite
    ├── Weather Tool
    ├── News Tool
    ├── Camera / Vision Tool
    └── General Conversation → GPT-5.6 Terra
    ↓
Response / Action
    ↓
Piper TTS
    ↓
Speaker

Known commands should use deterministic local routing whenever possible. General conversation should go to GPT.

Use the same wake word as AIA. Do not create a new wake-word system.

Expected flow:

Assistant idle
     ↓

     ↓
Start recording
     ↓
User speaks command
     ↓
Endpoint detected
     ↓
STT

The microphone should not continuously send user speech to GPT.

8. Language Support

Support:

  • English
  • Mandarin
  • Cantonese

Language should be determined per utterance following AIA's architecture. Do not force the user to select a language mode.

9. STT

Reuse AIA's STT architecture as much as possible. Use the existing tested implementation first and benchmark alternatives before replacing it.

10. TTS

Reuse AIA's Piper TTS implementation. The assistant should speak responses appropriately for English, Mandarin, and Cantonese interactions.

11. OpenAI GPT-5.6 Terra

The conversational LLM is OpenAI GPT-5.6 Terra through API.

User Speech
    ↓
STT
    ↓
Command Router
    ↓
OpenAI API
    ↓
GPT-5.6 Terra
    ↓
Response
    ↓
Piper
    ↓
Speaker

Initialize the API client during startup. Do not create a new client for every request. Store credentials securely and never hard-code API keys.

12. "LLM Loaded to RAM at Boot"

Because GPT-5.6 Terra is accessed through an API, it cannot literally be loaded into Raspberry Pi RAM like a local model.

Interpret the requirement as:

  • Initialize the OpenAI API client at boot.
  • Initialize persistent HTTP/API resources at boot.
  • Load local application resources at boot.
  • Keep the API client ready for requests.
  • Do not repeatedly initialize expensive resources for every conversation.

Do not download GPT-5.6 Terra to the Raspberry Pi.

13. General Conversation

The assistant should support normal conversation and reasonable short-term context, including follow-up questions. Do not retain unlimited history; use a configurable context/window limit.

14. Tool-Based Architecture

Use controlled tools/functions such as:

get_weather()
get_local_news()
capture_camera_image()
describe_camera_image()
open_kodama()
execute_kodama_command()
get_current_time()

GPT must not directly execute arbitrary shell commands.

15. Weather

Location: San Jose, CA 95127.

Use a current online weather source rather than relying on GPT's static knowledge. Support current conditions and forecast requests. Cache weather data for a short period so the screensaver does not continuously hit the API.

16. Local News

Implement current local news focused on San Jose, Santa Clara County, and Silicon Valley. Retrieve current information online and have GPT summarize the results. Prefer 3–5 concise stories instead of reading entire articles through TTS.

17. Bedtime Story

Generate child-friendly, calm, positive bedtime stories suitable for TTS. Allow the user to specify characters, themes, length, and setting.

18. Camera

Use Raspberry Pi Camera Module 3. Support requests such as "What do you see?", "Describe what the camera sees", and "What's in front of me?"

Voice command
    ↓
Camera capture
    ↓
OpenAI vision-capable API
    ↓
Description
    ↓
TTS

Do not continuously upload camera frames to OpenAI. Capture/send an image when the user requests visual understanding.

19. Camera Image Description

  1. Capture a new image.
  2. Do not use an old cached image unless explicitly requested.
  3. Send the image to the OpenAI vision-capable API.
  4. Ask for a concise description.
  5. Return the response through TTS.
  6. Show the description on the 1280×800 display if appropriate.

20. Person Detection

Use Camera Module 3 for local person detection. This is separate from GPT image understanding.

Do not continuously send camera images to OpenAI for presence detection. Prefer local detection using the Raspberry Pi AI HAT+ 2 and an appropriate accelerated model.

21. Person Detection State Machine

Use hysteresis/debounce so one missed frame does not immediately change the UI state.

No person
    ↓
Person detected in several consecutive frames
    ↓
PERSON_PRESENT

Person present
    ↓
No person detected for several frames/seconds
    ↓
PERSON_NOT_PRESENT

Make thresholds configurable and tune them on the actual Raspberry Pi.

Commands affecting the operating system must retain confirmation behavior. GPT must not directly execute shutdown, reboot, or other destructive commands.

35. Development Procedure

Phase 1 — Repository Analysis

  1. Inspect AIA.
  2. Inspect Kodama-Lite.
  3. Map the architecture.
  4. Identify reusable components.
  5. Identify AIA/Kodama interfaces.
  6. Identify systemd services.
  7. Identify UI architecture.
  8. Identify existing voice commands.
  9. Identify wake-word implementation.
  10. Identify STT/TTS implementations.

Produce an architecture report before making major modifications.

Phase 2 — Raspberry Pi Hardware Verification

SSH into fuwenxu@aipi5.local and verify the Pi, AI HAT+ 2, Camera Module 3, TI microphone, speaker, 1280×800 display, network, Kodama-Lite, and AIA dependencies.

Phase 3 — Reproduce AIA Voice Loop

Wake word → STT → Existing Kodama command → TTS

Verify English, Mandarin, Cantonese, microphone, speaker, and wake word before adding GPT.

Phase 4 — Build New Assistant Shell

Create the application, configuration, state machine, router, logging, and UI while preserving AIA's architecture.

Phase 5 — GPT-5.6 Terra Integration

Implement OpenAI API client, authentication, model requests, conversation context, timeout/retry policy, error handling, and response handling.

Phase 6 — Tool Calling

Add tools one at a time: Weather → News → Time → Camera. Unit-test each before integrating it into voice control.

Phase 7 — Kodama Integration

Connect the new assistant to Kodama-Lite and verify all existing commands in English and Mandarin.

Phase 8 — Camera Vision

Implement camera capture → OpenAI vision request → description → TTS. Test camera and API failure behavior.

Phase 9 — Person Detection

Implement local person detection and tune debounce behavior on the actual Pi.

Phase 10 — Screensaver

Implement no-person timeout → 1280×800 weather/time screen → person return → normal UI.

Phase 11 — Boot Integration

Install as a service and test cold boot, reboot, and service restart.

39. Final Rules for Claude Code

  1. Inspect before modifying.
  2. Use the current AIA repository as the primary voice architecture reference.
  3. Use the current Kodama-Lite repository as the music-control/application reference.
  4. Reuse the AIA wake word.
  5. Reuse AIA STT unless testing proves a better alternative is required.
  6. Reuse AIA Piper TTS.
  7. Preserve existing Kodama voice commands.
  8. Do not duplicate Kodama's internal functionality unnecessarily.
  9. Use GPT-5.6 Terra through the OpenAI API.
  10. Do not attempt to download GPT-5.6 Terra onto the Raspberry Pi.
  11. Initialize reusable resources at startup.
  12. Use deterministic routing for known commands.
  13. Use GPT for open-ended conversation and tool selection.
  14. Do not allow GPT to directly execute arbitrary shell commands.
  15. Protect shutdown/reboot/destructive commands with explicit confirmation.
  16. Use local person detection rather than continuously uploading camera frames.
  17. Use AI HAT+ 2 where it provides meaningful local acceleration.
  18. Design the UI specifically for 1280×800.
  19. Do not use the old 1920×440 Kodama display assumption for the new assistant UI.
  20. Keep weather/news/camera functionality modular.
  21. Keep API keys out of source control.
  22. Measure performance on the actual Raspberry Pi 5.
  23. Test each subsystem before integrating the next one.
  24. Do not declare completion until all acceptance criteria pass.
  25. If a major architectural change is necessary, explain why before making it.
  26. Do not remove existing functionality simply to make implementation easier.

40. Important Architecture Clarification

The current AIA repository should be treated primarily as the voice/control foundation. The new project should add GPT-5.6 Terra as the conversational and vision layer rather than assuming an existing local LLM implementation that needs to be replaced.

The new assistant UI must target 1280×800. Do not inherit the old 1920×440 display geometry from Kodama-Lite.
